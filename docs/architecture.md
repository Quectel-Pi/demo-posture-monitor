# 系统架构

> 实现依据：《RK3576 坐姿检测与护眼提醒_完整实施方案》§3（软件架构）、§4（算法）、
> §5（护眼业务）、§6（模块接口）、§11（数据结构与状态机）。
> 本文只描述**已经实现并实测**的内容；未实现的部分在末尾「边界」里明确列出。

## 1. 进程拓扑

```
┌──────────────────────────────────────────────────────────────────────┐
│ posture-guard.service   (systemd 系统服务, User=posture, 无图形会话)  │
│                                                                      │
│  CaptureThread ──最新帧槽(容量1)──> MonitorThread                    │
│   V4L2/OpenCV                         ├─ RknnPoseEngine   (NPU)     │
│   指数退避重连                        ├─ PostureAnalyzer  (几何+迟滞)│
│                                       ├─ EyeCareMonitor   (20-20-20) │
│                                       ├─ ReminderManager (冷却/合并) │
│                                       ├─ StatsStore       (JSONL)    │
│                                       └─ Notifier ─┐                 │
└─────────────────────────────────────────────────── │ ────────────────┘
                                                     │ AF_UNIX (JSON 行)
                                                     │ /run/posture-guard/status.sock
┌────────────────────────────────────────────────────▼───────────────┐
│ posture_guard_ui.py  (用户会话, GTK4, 全屏)                        │
│  订阅状态 / 接收通知 / 画骨架 / 底部按钮（校准·免打扰·已休息）     │
└────────────────────────────────────────────────────────────────────┘
```

**为什么拆成两个进程**：systemd 系统服务拿不到 `DISPLAY` / `WAYLAND_DISPLAY` 权限，
在自动登录、多用户、无屏场景下会不稳定（实施方案 §13.3）。拆开后后台服务完全无界面，
界面挂了也不影响计时与检测。

**界面拿到的画面**：socket 上有两类消息 ——
`{"type":"status"}`（每 0.5s，含 17 个归一化关键点）与
`{"type":"video"}`（默认 10fps，`<w>x<h>` + base64 JPEG）。
界面用 `Gtk.Picture` 显示视频、透明 `Gtk.DrawingArea` 叠骨架。

画面**只在本机内存与本地 unix socket 里流转**：不落盘、不出网，
`privacy.save_raw_video` / `save_face_images` 仍强制为 false（§18.2）。
不想要画面就设 `ui.stream_video: false`，界面退回纯骨架模式。

## 2. 线程模型

| 线程 | 职责 | 频率 |
|---|---|---|
| capture | V4L2 取帧、写「最新帧槽」 | 摄像头原生（本机 15–30fps，实测 20fps） |
| monitor | 抽帧推理 → 规则 → 计时 → 通知 → 推送状态 | 推理上限 `camera.infer_fps`（默认 15，板上生产置 25） |
| main | 信号、退出编排、`--run-seconds` | — |

两条硬规则：

1. **视频流绝不排队**。帧槽容量为 1，推理慢就覆盖旧帧（§14.3）。实测 NPU 一帧 17–25ms，
   采集 50ms 一帧，永远不会积压。
2. **业务计时用 `steady_clock`**，与 FPS 无关。即使推理某帧失败、摄像头短暂断流，
   20 分钟用眼计时也不会跑偏（§3.2）。日志与统计另用墙上时钟。

## 3. 数据契约

`include/posture/Types.hpp` 是唯一的公共数据结构：

| 结构 | 说明 |
|---|---|
| `Frame` | BGR 图 + `frame_id` + `steady_clock` 时间戳 + 墙上时间 |
| `PersonPose` | 人体框 + 17 关键点（原图坐标）+ 人物置信度 |
| `PostureMetrics` | 肩线角度、肩宽、头肩归一化偏移、宽度比、手腕-鼻子距离 |
| `PostureObservation` | 状态 + 指标 + **本帧新激活的规则** + 仍激活的规则 |
| `Baseline` | 个人校准基准 + 摄像头 ID + 分辨率 + 模型 SHA256 |

**三态分离**（§6.3 强制要求）：`NORMAL`（姿态正常）、`USER_AWAY`（画面里没人）、
`UNKNOWN`（有人但关键点不可信/多人/机位不对）是三件不同的事，绝不混用。

## 4. 姿态判定

### 4.1 关键点有效性

w8a8 量化模型的关键点 `conf` 通道被整体量化摧毁（scale≈3.19，恒为 0），
因此**关键点可信度用人物框置信度做代理**，并且加了三道几何闸门
（都在 `PostureAnalyzer::ComputeMetrics`）：

1. 鼻点、双肩点必须高于 `joint_confidence`；
2. 肩宽 `>= 24px`；
3. **取景门**：鼻子不能贴画面上边缘、双肩不能贴边、鼻子到肩线的距离要
   `>= min_head_gap`（默认 **0.08** × 肩宽，可配）。不满足就判 `UNKNOWN` 并给出原因。

第 3 条的门限为什么这么低：摄像头装在显示器上方**往下俯拍**时，头肩纵向距离
天然就小；人一低头更是直接压到肩线上 —— 那恰恰是要检测的「低头」信号，
不是该丢弃的坏帧。早期版本写死 0.22，结果把俯视机位下的低头帧全扔了，
表现为「校准采样不足」+ 低头永远检测不到（见 `docs/troubleshooting.md` §12）。
现在的 0.08 只用来挡「模型把鼻子检到肩线上」这种明显错检。

### 4.2 特征量

| 特征 | 定义 | 用途 |
|---|---|---|
| `shoulder_angle_deg` | `atan2(dy, dx)`，折叠到 `[-90°, 90°)` | 高低肩 |
| `shoulder_dev_deg` | 与个人基准的角差，同样做 180° 周期折叠 | 高低肩（判据） |
| `head_offset_y` | `(鼻子Y − 肩中点Y) / 肩宽`（负值，鼻子在上方） | 低头（近似量） |
| `ear_angle_deg` | 左右耳连线相对水平的角度（折叠到 ±90°） | **歪头（主判据）** |
| `head_axis_deg` | 肩中点→鼻子连线相对竖直方向的偏角 | 仅诊断（俯视下不稳定，见下） |
| `width_ratio` | `肩宽 / 画面宽` | 离屏太近（趋势，不是物理距离） |
| `wrist_to_nose` | `min(左右手腕到鼻子距离) / 肩宽` | 托腮 |

除 `shoulder_dev_deg` 外都是**归一化到肩宽**的量，人走近走远时数值基本稳定（§4.3）。

**歪头为什么用耳线而不是「肩中点→鼻子」的偏角**：后者是
`atan2(nose.x - sx, sy - nose.y)`，俯视机位下 `sy - nose.y` 很小（分母趋近 0），
横向几个像素的噪声就能把角度放大几十度 —— 实测同一个坐姿下摆动 **−48° ~ +9°**，
完全不能当判据。耳线是一条横跨头部的基线，与肩线同样稳定（实测摆动 6°）。

**低头阈值为什么是「比例」而不是固定值**：头肩纵向距离随摄像头俯仰角变化极大 ——
直视机位基准约 −0.9 肩宽，显示器上方俯拍只有 −0.20。固定的 0.35 在俯视机位下
**永远达不到**（鼻子压到肩线上最多只能降 0.20），低头检测直接失效。
改成「基准距离 × 55%，钳在 0.10~0.45」后与机位无关：俯视得 0.11，直视得 0.45。

**托腮为什么要加「手腕必须高于肩线」**：坐在桌前打字时手在桌面上，图像里
手离胸/脸并不远（俯视机位尤其明显），只比「手腕到鼻子的距离」会一直误报。
实测手放桌面时手腕比肩线低 **95~109% 肩宽**，托腮时一定高于肩线，所以用
`wrist.y < 肩线y - 0.1×肩宽` 作为门控，不满足就把 `wrist_to_nose` 置 99（不触发）。

### 4.3 规则与迟滞

分两层：**传统规则路径**（`HoldRule`，“持续 N 秒才激活、恢复到 M 秒才解除”，§11.3）与
**逐姿势画像路径**（有时间窗投票 + 级联迟滞）。有画像文件时走后者。

`HoldRule` 传统路径（阈值与保持时间均为**工程初始值**，实际以 `config/posture.yaml` 为准）：

| 规则 | 触发 | 恢复 | 持续 | 优先级 |
|---|---|---|---|---|
| 高低肩 `shoulder_tilt` | 偏离基准 > 12° | < 8° | 0.5s（恢复 0.35s） | 40 |
| 低头/趴桌 `head_down` | 头肩纵向比基准低 > 25% 基准距离（钳在 0.10~0.35 肩宽） | 一半 | 0.5s | 50 |
| 歪头 `head_tilt` | 耳线与基准的夹角 > 18° | < 10.8° | 0.5s | 30 |
| 离屏太近 `too_close` | 肩宽占比 > 基准 × 1.35 | < 1.24× | 0.5s | 20 |
| 托腮 `hand_on_face` | 手腕-鼻子 < 0.95 肩宽 | > 1.19 | **3.0s** | 60 |

> 托腮的保持时间单独拉长到 3s：抬手拿东西的瞬时动作不该报出来。

### 4.3.1 逐姿势画像路径（实际生效的那条）

规则由 `scripts/pose_capture.py --guided` 采样本后算出，存在
`/var/lib/posture-guard/postures.txt`，**阈值不是手调的**（取正常类与目标类中位数之间的最优分割点）。

两层防抖：

| 层 | 机制 | 参数 |
|---|---|---|
| 界面判定 | **时间窗投票** | 进入 0.6s / ≥80% 帧；退出 1.2s / ≥70% 帧 |
| 语音播报 | **连续帧计数** | `notification.posture_frames: 10` 帧 |

> 为什么不用「连续保持 N 秒」：那个模型下**一个噪声帧就把计时清零**，N 必须很大才稳，
> 延迟和精度被绑死。投票制下单帧噪声只影响一票，实测确认时间从 1.5~2.5s 降到 0.2s。

> 高低肩/低头/歪头**必须先有个人基准**；没有基准时只跑距离和托腮两条，
> 然后在状态里明确写「未校准」，绝不假装判过了（§4.6 / §11.4）。

### 4.4 主用户选择

1. 过滤：框面积、置信度、ROI、几何合理性；
2. **按 IoU/中心距去重**：w8a8 的 conf 通道很粗，同一个人会被多尺度重复检出，
   框中心抖动几十像素、IoU 达不到 NMS 阈值。不去重会把一个人判成「多人」；
3. 去重后仍有两个人尺寸接近 → `ambiguous`，不做个体判定（§11.4 / TC-11）。

### 4.5 基准漂移检测（挪了摄像头必须重校准）

`BaselineMatches()` 只能比对摄像头 ID / 分辨率 / 模型 SHA256。**摄像头没换、
只是人把它挪了个位置**时这三项都不变，它会认为基准有效 —— 于是所有相对基准的
阈值全部算偏。

所以启动后收集 20 个有效帧，取 `width_ratio` 与 `head_offset_y` 的**中位数**，
与基准比对：

| 判据 | 门限 |
|---|---|
| 肩宽占画面宽的比例变化 | > 1.8 倍或 < 0.55 倍 |
| 头肩纵向偏移变化 | > 0.45 个肩宽 |

命中就作废基准、自动进入重新校准，并在日志里说清是哪个量变了：

```
[WARN] 校准基准已失效：画面里肩宽占比 0.40，校准基准是 0.11（差 3.7 倍）——摄像头或人就位变了
[WARN] 旧基准会让所有阈值都算偏，现作废并自动重新校准
```

只检查一次（用中位数），避免用户中途换个坐姿就被反复判为漂移。

### 4.5.1 摄像头 roll（绕光轴转动）：只提示，不自动重校准

上面两项判的是「距离」和「俯仰」，**测不出摄像头绕光轴转了多少**。摄像头被手拧歪时
画面整体旋转，肩线角随之变化 —— 实测出现过「肩线稳定 29.4°、基准 0.0°」的情形
（读数稳定说明不是检测噪声）。

这里有个必须分开处理的原因：

| 情况 | 该怎么做 |
|---|---|
| a) 摄像头被转动/放歪 | 重新校准 |
| b) 用户本人正歪着坐 | **绝不能重校准** —— 那等于把坏姿势记成正常，之后永远不报警 |

系统分不清 a 和 b，所以 `CheckRollHint()` **只产生提示，不作废基准**：

```
[WARN] 基准提示：肩线与校准基准差 29°（当前 29.4°，基准 0.0°）。
       若是摄像头被转动/放歪了，请坐正后重新校准；若你确实正歪着坐，忽略此提示
```

阈值 15°（低于此量级既可能是轻微歪坐，也可能是检测抖动，不值得打扰）。
提示同时出现在 `status.baseline_hint` 字段、`scripts/status.sh` 输出里，由人判断。

### 4.6 摄像头参数协商

不硬编码采集参数，先问设备（`src/V4l2Probe.cpp`）：

```
VIDIOC_QUERYCAP → 是不是采集节点（/dev/video74 这类 metadata 节点会被排除）
VIDIOC_ENUM_FMT → 支持的像素格式
VIDIOC_ENUM_FRAMESIZES → 每个格式的尺寸
VIDIOC_ENUM_FRAMEINTERVALS → 每个尺寸的帧率
        ↓
ChooseCapture(): 格式优先压缩(JPG省 USB 带宽) → 尺寸取最接近面积 → 帧率取不超期望的最大值
        ↓
cap.set(FOURCC) 再 cap.set(WIDTH/HEIGHT)     ← 顺序不能反
        ↓
日志记录「请求值 vs 实际值」，只有真不一致才 WARN
```

本机这块 icSpring 只给 `YUYV 640x480 @ 30/25/20/15/10/5fps`，一个格式一个分辨率。
日志：`摄像头能力：icspring camera [YUYV(640x480) ]` +
`实际 640x480@20fps 格式 YUYV（请求 640x480 YUYV）`。

### 4.7 离屏过近：趋势判据，不测距

**本系统不做距离测量。** 摄像头没有 ToF、没有深度传感器，单目图像也无从得到
可靠的厘米数（实施方案 §1.1 / §4.5 明确写了这一点）。

所以 `too_close` 判的是**取景变化**，不是距离：

```
width_ratio = 肩宽像素 / 画面宽
当前 width_ratio > 校准基准 width_ratio × too_close_ratio_rel(默认1.35) → 判「离屏过近」
```

含义是「比你校准时靠近了约 26%」，不是「你现在离屏幕 31 厘米」。

#### 为什么必须用相对值

`width_ratio` 的绝对值强依赖摄像头 FOV，完全不可跨设备/跨机位移植：

| 机位 | 正常坐姿时的 width_ratio |
|---|---|
| 旧 icSpring（直视、视野窄） | 0.11 |
| 旧 icSpring（人贴很近） | 0.78 |
| 现 UGREEN（显示器上方俯拍） | 0.35 ~ 0.50 |

早期版本把阈值写死成 `0.75`（来自第一台摄像头的观测值）。换到现在的俯视机位后，
**正常坐着就已经 0.42**，要触发 0.75 需要占比涨到 2 倍以上 —— 用针孔模型反推
那是 19cm（脸贴屏幕），规则等于失效。改成「基准 × 1.35」后与机位无关。

#### 为什么必须做时间平滑

肩宽是「左肩坐标 − 右肩坐标」两点之差。w8a8 量化下，模型某一帧把肩点检偏几十像素
（把手臂/衣服边界当成肩），width_ratio 就会翻倍 —— 实测人完全没动时
在 **0.377 ~ 0.524** 之间跳（±39%），`too_close` 跟着反复触发/解除：

```
某帧   sh_l(0.75,0.58) sh_r(0.37,0.51)  → 肩宽 0.386
下一帧 sh_l(0.78,0.60) sh_r(0.27,0.62)  → 肩宽 0.510   ← 右肩跳了 64 像素
```

取景距离是慢变量（人不会 100ms 移动 15cm），所以对 `width_ratio` 做 **3 帧滑动中值**：
单帧离群被滤掉，持续偏移仍能跟上（单元测试两边都断言）。平滑后极差从 0.147 降到 0.016。

> 早期版本曾在此基础上做过「单目距离粗估」（`Z = K / width_ratio`）并在界面显示厘米数。
> 因为误差达 ±20~30%、且量的是「到摄像头」而非「眼睛到屏幕」的距离，
> **已被移除**（2026-10-29）。要厘米级精度只能加 ToF。

## 5. 护眼业务

状态机（§5.2 原文实现，`src/EyeCareMonitor.cpp`）：

```
ABSENT  --在座连续 2s-->  ACTIVE（开始累计）
ACTIVE  --累计 >= 1200s--> BREAK_DUE（发一次休息提醒）
ACTIVE  --无人连续 10s-->  ABSENT（会话结束、清零）
BREAK_DUE --用户点「已休息」/ 自动策略满 20s--> ACTIVE（重新计时）
BREAK_DUE --无人连续 10s--> ABSENT
```

`reminder_policy` 支持两种：`manual_ack_or_session_reset`（默认，等人确认）
和 `auto_restart`（休息满 `far_look_s` 自动开始新一轮）。

**明确不做的事**：不去判断「用户是否真的在看远处」。摄像头看到人在这里，
不能证明眼睛放松了。所以提醒是提醒，不是测量（§5.1）。

## 6. 提醒去重

`ReminderManager`：

* 同类提醒 `notification.cooldown_s`（默认 60s）内不重复；
* 同一帧多条规则同时成立 → 合并成一条通知，取优先级最高的作标题；
* 「忽略 15 分钟」全局免打扰（`scripts/snooze.sh` 或界面按钮）。

## 7. 输出

| 通道 | 内容 | 位置 |
|---|---|---|
| journald | 生命周期、校准、告警、错误 | `journalctl -u posture-guard` |
| AF_UNIX | `{"type":"status",...}` 每 0.5s；`{"type":"video",...}` 10fps；`{"type":"notification",...}` 即时 | `/run/posture-guard/status.sock` |
| JSONL 统计 | 每 10s 一条 tick + 每次告警一条 alert | `/var/lib/posture-guard/stats/stats-YYYY-MM-DD.jsonl` |

界面命令（客户端 → 服务）：`{"cmd":"ack"}`、`{"cmd":"snooze","minutes":15}`、
`{"cmd":"clear_snooze"}`、`{"cmd":"calibrate"}`。

### 7.1 语音播报（离线 WAV）

语音不在 C++ 服务里，在桌面 UI 进程（`ui/posture_guard_ui.py` 的 `VoicePlayer`）：
收到 `{"type":"notification"}` 后按 `key` 用 `paplay` 播放
`assets/voice/<key>.wav`。白名单 6 个 key：`shoulder_tilt`、`head_down`、
`head_tilt`、`too_close`、`hand_on_face`、`rest`；key 不在白名单直接拒绝，
所以路径穿越（`../../x`）进不来。播放不阻塞 GTK、不堆积队列
（2s 节流；同一姿势不重播，换姿势则立即打断旧语音；`rest` 不受限制）。

素材是**预生成的 24kHz mono 16bit WAV**，运行期完全离线、板端零新依赖。
两条生成路径产物同名同格式，可随时互换：

| 脚本 | 引擎 | 音色 | 需要网络 |
|---|---|---|---|
| `scripts/make_voice_assets_neural.py` | edge-tts `zh-CN-XiaoxiaoNeural` | 神经女声，接近真人 | 烘焙时一次 |
| `scripts/make_voice_assets.py` | libespeak-ng `cmn` | 机械音 | 不需要 |

文案只定义在 `make_voice_assets.py` 的 `PROMPTS` 里，神经脚本 import 复用，
避免两处漂移。两个脚本的归一化目标一致（RMS ≈ 20%、峰值 ≤ -1dBFS），
详见 [troubleshooting §17.3](troubleshooting.md)。

**为什么不用单遍 `loudnorm`**：ffmpeg 4.4 的 `loudnorm` 对 3 秒以内的短句会算错
增益（实测把 RMS 从 19% 压到 3.6%，小了 14dB，反而听不见）。所以神经脚本用
「测量 integrated loudness → 换算增益 → `alimiter level=false`」这套确定性链路。

## 8. 配置

`/etc/posture-guard/posture.yaml`，解析器是内置的 YAML 子集实现
（`src/Yaml.cpp`，只支持本项目用到的写法：嵌套 map、标量、行内数组、注释）。
不用 yaml-cpp/nlohmann，因为板端没有这些包也没有外网。

隐私红线：`privacy.save_raw_video` / `save_face_images` 只要有一个是 `true`，
程序**直接拒绝启动**（§18.2）。

## 9. 边界（本文档不吹的部分）

* 正面单目摄像头**测不出脊柱曲度**，也不测真实的低头角度。`head_down`、`head_tilt`
  是肩宽归一化的近似量，界面与日志都标了 approx 的含义（§1.1 / §16.7）。
* `width_ratio` 只是「离屏过近趋势」，不是厘米距离。要真实距离需要 ToF（V2）。
* 没做人脸 Landmark、没有相机标定、没有 ToF/环境光。
* 视频流是 base64 编码进 JSON 的（简单可靠，但比裸二进制多 33% 带宽）；
  640×480 q70 ≈ 540KB/s，本机 unix socket 完全够，换到网络传输要改成二进制帧。
* 没做 Qt 界面，界面是 GTK4 单进程（同一台一体机够用）。
* 多人场景只支持「锁定主用户」，不支持同时判定多个人。
